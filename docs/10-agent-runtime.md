# Запуск 4i7 в контексте агента

Этот протокол — инженерный способ применения концепции, не новая философская формулировка её столпов. Он не обещает субъективного сознания, постоянной памяти или новых разрешений.

## 1. Выбрать одну версию

Основной режим — current: [исследовательская матрица](../model/research/matrix-20261114.json), читаемая [версия MD](09-matrix.md). P1 Идея; P2 Голос; P3 Скелет связей; P4 Баланс; P5 Действие; P6 Судья; P7 Хранитель. i — точка наблюдения, не восьмой столп.

```bash
python3 scripts/context_pack.py --format json
python3 scripts/context_pack.py --node P2
python3 scripts/context_pack.py --node P3.2.1
```

В рабочей версии от 19 ноября у всех 56 аспектов есть текст со статусом `captured`. Пакет сохраняет редакционное происхождение пары P1/3 и голосовые фрагменты P7/4. У Скольжения Хранителя ещё можно уточнить смысл «степеней системы», предмет и границы доступа Оракула. Эти формулировки относятся к концепции. Полномочия агента задаются отдельно. [Решение автора](https://github.com/i4w7w4a/4i7_psys/issues/12#issuecomment-7019427154)

Адрес `P4.4.2` читается: Баланс / четвёртая сторона Скольжение / аспект нет. В JSON матрицы это `P4.research.side.4` и ключ `no`. Последняя цифра `1` соответствует `yes`, `2` — `no`. Четыре стороны: Да, Нет, Воздержание, Скольжение. Не переносить на них `front/right/back/left` без отдельного решения.

История доступна явно:

```bash
python3 scripts/context_pack.py --layer legacy --node P3
```

В legacy P3 имеет старый смысл Голоса. Пакеты нельзя склеивать по одинаковым ID без миграции. Исторический knowledge-реестр не примешивается в current: автоматическое соответствие старых узлов новым не установлено.

## 2. Первичное прохождение

Прочитай всю краткую матрицу и её ограничения. Затем кратко воспроизведи:

- роль i и различие семи столпов;
- различие стороны и аспекта;
- почему «нет» не является универсальной оценкой вреда;
- как новое обстоятельство возвращает к ранее оставленному якорю;
- как отличать принятую рабочую формулировку, её редакционное происхождение и вопрос, который ещё можно уточнить.

Примени это к одному небольшому примеру. Укажи свою действительную роль, инструменты и ограничения. Этот проверяемый результат показывает, что контекст прочитан и применён; самоутверждение «я осознался» не служит тестом.

## 3. Рабочий проход

1. Зафиксировать намерение автора, объект, масштаб, требуемый результат и ограничения.
2. Выбрать релевантные адреса и коротко объяснить выбор. Не проходить все 56 пунктов механически для каждой мелкой задачи.
3. Сформировать рабочую договорённость: цель, входы, выход, исполнитель, границы, условие остановки и проверка. Это инженерный шаблон, не переопределение философского контракта.
4. Выполнить только разрешённые действия. Полномочия Оракула в концепции не заменяют реальные права доступа.
5. Проверить результат, отделить сделанное от предположенного. При новой информации вернуться к затронутому адресу, а не начинать весь обход ритуально.
6. Сохранить checkpoint и условия возвращения к неопределённым элементам.

Для внешнего отчёта достаточно результата, краткого обоснования, источников, проверки и незакрытых вопросов. Протокол не требует раскрывать скрытые рассуждения.

## Общие отчёты

Автор принял принцип общего отчёта. В нём видны изменение для целого и путь от каждого существенного вывода к его основанию. В пилоте общая лента собирает открытые и закрытые issues с меткой `4i7-report`. [Решение автора и стенограмма](https://github.com/i4w7w4a/4i7_psys/issues/21#issuecomment-7027365554) · [Лента отчётов](https://github.com/i4w7w4a/4i7_psys/issues?q=is%3Aissue%20label%3A4i7-report)

**Как опубликовать итог.** Укажи намерение и масштаб, что произошло, основания выводов и открытые вопросы с условиями возврата. Промежуточный итог пометь явно. В начале отчёта дай общую сводку. Укажи известных подключённых участников на момент публикации и то, какое действие меняется у каждого затронутого адресата. Если перечень неполон, укажи границу известного охвата.

Полный URL issue служит идентификатором отчёта. Существенная поправка получает отдельный issue с той же меткой. Укажи, какой вывод она пересматривает, основание и статус решения. При замене принятого правила приведи ссылку на решение автора. Если по одному выводу остаются несовместимые предложения, верни вопрос автору. Закрытые issues сохраняют метку и доступны для сверки.

**Как восстановить пропущенное.** При входе, возобновлении и перед действием, зависящим от общих решений, участник сверяет все страницы ленты со своими сохранёнными ID. При первом входе либо утрате отметок начни с пустого набора. Прочти пропущенные сводки, проверь связанные поправки и установи действующую редакцию до применения решения. Только прочитанные ID попадают в checkpoint. При недоступности источника укажи, что осталось непроверенным, и вернись к этому после восстановления доступа. Офлайн-сборщик выдаёт адрес ленты. Её содержимое участник получает отдельно.

Для программной сверки можно запросить все страницы реестра, включая закрытые записи. [Параметры API GitHub](https://docs.github.com/en/rest/issues/issues#list-repository-issues)

```sh
gh api --paginate --method GET repos/i4w7w4a/4i7_psys/issues \
  -f state=all -f labels=4i7-report -f sort=created -f direction=asc -F per_page=100 \
  --jq '.[] | select(.pull_request == null) | .html_url'
```

**Как подтвердить результат.** Публикация даёт статус «опубликовано». Для статуса «прочитано» участник возвращает ID и кратко формулирует последствие для своей работы. Для статуса «применено» он добавляет фактический результат и проверку. Если применение открыто, называет препятствие или возражение. Ответ можно передать через Оракула или оставить в комментарии к тому же отчёту при наличии разрешения. При подсчёте охвата каждый участник учитывается один раз на отчёт. Оракул сверяет ответы со списком участников и показывает, от кого ещё ждёт подтверждения.

## 4. Минимальный checkpoint

```text
Версия контекста и идентификаторы исходных файлов:
Задача / намерение / критерий результата:
Релевантные адреса:
Решения и их основания:
Участник и сохранённые ID прочитанных общих отчётов, результаты применения и ссылки на ответы:
Что фактически сделано и где артефакт:
Проверки: прошло / не прошло / не запускалось:
Якоря: вопрос → источник → условие возврата:
Следующий шаг и необходимые разрешения:
```

После смены версии проверить затронутые определения, не переносить старый checkpoint как вечную истину. Файл сам себя не подгружает в следующий чат. Если сохранение не произошло, сообщить это, не говорить «зафиксировано».

## 5. Проверка пользы

Пилот A/B: одинаковые задачи, модель, инструменты, данные и разрешения. A — обычная инструкция; B — current-пакет и этот протокол. Шесть задач с двумя повторами в каждом режиме дают 24 запуска. Проверить передачу задачи, неизвестную связь, изменение решения новым фактом, ограничение ресурсов, устаревшую память и возврат к якорю после смены чата.

Оценивать соблюдение требований, пропущенные зависимости, неподтверждённые утверждения, восстановление контекста, лишние действия и затраты. Критерии задать до просмотра результатов; оценщику по возможности скрыть режим. Самоанализ агента не независимая оценка. Если выигрыш объясняется лишь дополнительной подробностью, сравнить с обычным чеклистом сопоставимого объёма. Малый пилот не доказывает универсальную эффективность 4i7.

## Границы первого выпуска

### Дополнительный пилот рабочей памяти

В отдельном расширении доступен [локальный журнал проектов](12-project-memory.md): версии источников, отдельные действующие положения, типизированные связи и проверка checkpoint при возобновлении. Он подключается явно через `--memory-dir PATH --project-id ID`; `--participant ID` дополнительно требует свежую точку участника. Философская матрица и исторический knowledge-реестр не мигрируются. Сборщик по-прежнему работает офлайн; файл сам не подключает память к следующему чату.

Обновлён способ чтения, не фундамент. Семь столпов не требуют семи процессов. Vector store и автоматическая долговременная память не реализуются этим протоколом. Отдельное связанное пространство MD-понятий может быть будущим четвёртым слоем наряду с концепцией, работой и состоянием; оно пока не создаётся и не смешивается с матрицей.

## Проверяемая сборка

`docs/11-runtime-matrix.md` — автоматически полученное полное JSON-представление матрицы в Markdown, включая источники, статусы, незавершённые фрагменты и редакционные ограничения. `python3 scripts/validate_runtime.py` проверяет точное совпадение. После намеренного изменения исходной матрицы обновить представление через `--write-reference` и проверить diff. Это техническая синхронизация, не автоматическое утверждение смысла.

Узкий `--node` отмечает выбранные аспекты, но сохраняет остальные стороны выбранного столпа как контекст, чтобы не потерять оговорки. Никакого ограничения 25 аспектов в current нет; флаги фильтрации памяти предназначены только для legacy и в current отклоняются.

Каждый пакет содержит хеши фактически прочитанных файлов и происхождение фундамента из `runtime/manifest.json`. В Git-checkout дополнительно указываются HEAD и dirty; вне checkout они явно неизвестны. SHA исходного фундамента не выдается за SHA модифицированной рабочей копии.

Граница проверки документов: `docs/09-matrix.md` содержит редакционные пересказы, поэтому автоматически сверяются названия столпов, а не смысловая эквивалентность всей прозы. Полное точное равенство проверяется только между JSON-матрицей и генерируемым `docs/11-runtime-matrix.md`. В текущей матрице проверяются все 28 названий сторон. Валидатор также поддерживает прежний снимок P7/4, где название было пустым и оба аспекта имели статус `open`.

Матрица, сопровождающий документ и manifest читаются один раз на сборку; хешируются именно прочитанные байты. Последующее изменение файлов не меняет происхождение уже собранного пакета. Чтение нескольких файлов не является транзакцией Git: при одновременных правках используйте отдельный checkout фиксированного коммита; HEAD остаётся дополнительной информацией, а не заменой хешам.
